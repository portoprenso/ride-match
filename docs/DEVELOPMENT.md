Turborepo development tasks are persistent and uncached. Declare contract build outputs and task dependencies explicitly. The root [`turbo.json`](../turbo.json) does this: `build` caches `dist/**` after dependency builds, `typecheck`, `lint`, and `test` emit nothing, and `dev` is persistent and uncached. No task depends on `dev`. No remote cache or release/deployment automation is needed initially. Bundle exports do not replace native build verification.

Install only justified dependencies during an authorized implementation task. Pin compatible versions and commit the workspace lockfile. Use Expo's recommended native dependency versions and run doctor after native integration changes.

Each bounded task should leave runnable behavior, focused tests where useful, updated current specs, and an honest work-log entry. Do not mark incomplete native checks as passing because a JavaScript export succeeds.

## Configuration

| Configuration | Use |
| --- | --- |
| `EXPO_PUBLIC_DATA_SOURCE=mock` | Select the mock data source centrally. Implemented (DATA-001-A): `mock` or `api`; `api` shows a configuration error |
| `EXPO_PUBLIC_MOCK_SCENARIO=active-neighborhood` | Initial deterministic scenario. Implemented: required with `mock`, a lowercase hyphenated key; the composition root rejects a key the simulator does not know (MOCK-001-B): `active-neighborhood` or `empty-neighborhood` so far |
| `EXPO_PUBLIC_APP_ENV=development` | Environment/demo labeling and analytics segregation. Implemented: `development`, `preview` or `production`; only `production` builds go without the demo controls (MOCK-001-C) |
| `GOOGLE_MAPS_ANDROID_API_KEY` (not `EXPO_PUBLIC_`) | Android map provider. Implemented (MAP-001-A): the Google Maps key, restricted to this app; set it only in `apps/mobile/.env.local` or the shell. Without it Android shows a notice instead of the map. Not configured yet |
| Future `EXPO_PUBLIC_API_BASE_URL` | Future adapter only; no API transport implemented now |

**Configuration files (DATA-001-A):** `apps/mobile/.env` (committed) sets the three public variables to the development values above. Override them in `apps/mobile/.env.local` (ignored) or the shell, then restart Metro: Expo reads `.env` when Metro starts and inlines `EXPO_PUBLIC_` values into the bundle. `src/config/appConfig.ts` validates them, with no defaults. A missing or invalid value, or `api`, replaces every route with a "This build can’t start" screen that names the variable; it never falls back to another data source. Jest loads no `.env`: `tests/setup/publicEnvironment.ts` sets the same development values. No credentials exist.

Public Expo variables are not secrets. API mode must fail clearly until implemented, never silently switch to synthetic riders. The scenario picker is limited to development/preview mock builds.

**Google Maps key for Android (MAP-001-A):** iOS draws Apple Maps and needs no key. Android draws Google Maps, which stops the app when a map appears without a key, so `app.config.ts` reads `GOOGLE_MAPS_ANDROID_API_KEY` and records only whether it was set (`extra.googleMapsAndroidConfigured`, read by `src/config/isMapProviderConfigured.ts`). Without it, Android shows "The map can't be shown in this build" with the sheet still working. To configure it:

1. In Google Cloud, create an API key, restrict it to Android apps with package `com.ridematch.dev` and the SHA-1 of the signing certificate (for development builds, `./gradlew signingReport` in `apps/mobile/android` prints the debug one), and restrict its APIs to Maps SDK for Android. Never paste the key into chat, docs, logs or tracked files.
2. Put `GOOGLE_MAPS_ANDROID_API_KEY=…` in `apps/mobile/.env.local` (ignored by Git). Expo CLI loads it when it evaluates the app configuration.
3. Regenerate the native project, since the key lives in the Android manifest (`apps/mobile/android/` is generated and untracked; remove it or run `pnpm exec expo prebuild --platform android --clean` in `apps/mobile`), then `pnpm mobile:android`. Restarting Metro alone changes the flag but not the manifest, and the app then stops when home opens.

The key goes through Expo's `android.config.googleMaps.apiKey`, which Expo keeps out of the public configuration served to the app; react-native-maps' own plugin options would have put it there.

Store future refresh credentials through SecureStore; keep access token in memory. Keep demo and production credential namespaces separate. Scenario reset clears demo state and this app's demo credentials only. No tokens or sensitive payloads in logs.

## Test strategy

Use Vitest for schema/contract checks, Jest with jest-expo and React Native Testing Library for feature behavior, and a small Maestro suite for native flows. Two test environments serve different needs: pure TypeScript contracts and Expo/native component integration. [Expo unit testing](https://docs.expo.dev/develop/unit-testing/)

| Layer | Important checks |
| --- | --- |
| Contracts | Invalid inputs, strict public/private fields, discriminated events/notifications, error envelopes |
| Mock operations | Expiry, capacity, atomic joining, idempotency, permissions, block effects |
| Feature integration | Auth continuation, create/cancel, match UI, joining, chat retries |
| Synchronization | Duplicate/out-of-order events, reconnect, logout/private-cache clearing, revocation |
| Native integration | Permission fallback, map gestures/markers, keyboard/sheets, local notification entry, taxi handoff |

Inject clocks and use deterministic failures. Advance fake time instead of sleeping in unit/integration tests. Test behavior, not copies of implementation details. Avoid exhaustive snapshots of trivial UI.

## Analytics boundary

Use typed `analytics.track(...)` events with bounded properties. Initially use an in-memory/no-op sink, inspectable in development. No vendor integration or external transmission is required.

| Event | Exact trigger | Stage and properties (ANALYTICS-001-A) |
| --- | --- | --- |
| `app_opened` | Start of a defined foreground session | view; — |
| `map_opened` | Main map first becomes visible in that session | view; — |
| `nearby_activity_exposed` | Fresh successful discovery renders; record zero/nonzero and count bucket | view; `countBucket` (`0`, `1`, `2-5`, `6-20`, `21+`), `truncated` |
| `nearby_marker_seen` | Peer marker visible for a minimum dwell; deduplicate per session | view; `kind` (`ride`, `group`) |
| `nearby_marker_tapped` | Peer marker tap | intent; `kind` |
| `destination_selected` | Search suggestion confirmed | intent; — |
| `ride_request_create_clicked` | User confirms creation intent | intent; `departureOffsetMinutes` (0, 5, 10), `pickup` (`device`, `manual`) |
| `ride_request_created` | Canonical create succeeds | success; `departureOffsetMinutes`, `pickup` |
| `ride_request_expired` | Authoritative expiry observed, once per request | observed; — |
| `match_found` | New valid match observed, once per match/version | observed; `level` (`possible`, `good`, `excellent`), `kind` |
| `group_join_clicked` | Join intent confirmed | intent; `kind` |
| `group_joined` | Canonical membership succeeds | success; `kind`, `memberCount` (2–4) |
| `group_leave_clicked` | Leave intent confirmed | intent; — |
| `group_left` | Canonical removal succeeds | success; — |
| `message_send_clicked` | User submits text | intent; — |
| `message_sent` | Canonical message accepted | success; — |
| `meeting_point_viewed` | Meeting-point detail opened | view; — |
| `taxi_open_clicked` | External handoff requested | intent; — |
| `taxi_opened` | OS accepts handoff; not proof of native opening or booking | success; — |
| `ride_completed` | Explicit completion mutation succeeds | success; `memberCount` |
| `user_reported` / `user_blocked` | Corresponding operation succeeds | success; `reason` (the four report reasons) / — |

Properties may include environment, application version, mock scenario ID, session ID, and pseudonymous installation/user identity. Do not accept unrestricted metadata. Exclude phone numbers, coordinates, destination search text, messages, report content, and credentials. Never emit success solely because a button was pressed.

Session/dwell thresholds should be defined and tested in ANALYTICS-001. Synthetic scenario traffic must remain distinguishable and excluded from future real-user metrics.

**Implemented (ANALYTICS-001-A):** `apps/mobile/src/analytics/`. Since MAP-002-A the composition root creates the client and the root layout starts it (`map_opened`, `nearby_activity_exposed` are the first tracked events).

- `events.ts`: the catalog above, one fixed set of required properties per event, built from contract enums and small whole-number ranges only. The types reject other properties at compile time, and `validateEvent` rejects an unknown event, an extra property (such as a coordinate, phone number, search text, message or report details) or a missing or out-of-range value at run time with an `AnalyticsEventError` that names the property but never the value. Nothing invalid is recorded. Stages: `view`, `intent` (asked for), `success` (only from the source's canonical result) and `observed` (a source change the user did not cause); `INTENT_SUCCESS_PAIRS` lists the five intent/success pairs. `countBucket` turns a visible count into a bucket, so no exact count is recorded.
- `createAnalytics.ts`: `track`, `trackOncePerSession` (such as `map_opened`), `trackOnce(key, …)` (such as one expiry per request; the key stays on the device), `markerVisible`/`markerHidden` and `setUser`. Every event carries its stage, session ID, sequence, time and context: environment, app version, mock scenario, `synthetic` (true on the mock data source), installation ID (`null` until one is stored) and pseudonymous user ID.
  - **Session:** `start()` begins the first one with `app_opened`, at once or on the first foreground. A return after `SESSION_TIMEOUT_MS` (30 minutes) or more in the background begins a new one; a shorter absence or iOS `inactive` continues it.
  - **Dwell:** a peer marker (never a cluster or the user's own) counts as seen after `MARKER_DWELL_MS` (1 second) of foreground visibility, once per target per session, recording only its kind. Going to the background pauses the dwell; hiding the marker cancels it.
- `sinks.ts`: `createMemorySink` (keeps the latest 500 for inspection), `noopSink`, and `selectAnalyticsSink` (memory in development and preview, nothing in production). Nothing leaves the device. `isRealUserEvent` keeps only production events from a real data source, so every mock event is excluded.
- `AnalyticsProvider` and `useAnalytics()` hand the client to features.

## Retention hypothesis

Hypothesis: users exposed to at least one nearby active ride engage and return more often than users seeing an empty map.

- Cohort by the first eligible successful map exposure, not a failed or loading screen.
- Distinguish zero visible peer activity from at least one visible peer activity item.
- Exclude own markers, stale data, failed loads, and mock sessions.
- Track clustered visible activity for the exposure metric without inventing individual marker impressions.
- D1/D7 are return sessions on UTC calendar day 1/day 7 after cohort entry.
- Preserve anonymous-to-authenticated association with pseudonymous IDs, never phone numbers.
- Instrumentation is verifiable now; actual retention requires a future analytics destination and real users.
