## Local backend (BE-001)

Use Node 24.17.0 / pnpm 11.28.2 and start Docker Desktop (Docker Engine with Compose v2 also works). From the repository root:

```bash
nvm use
pnpm install --frozen-lockfile
cp apps/api/.env.example apps/api/.env.local
pnpm db:up
pnpm db:migrate
pnpm start:api
```

Copy the example only for initial setup; preserve any existing local configuration. The example contains synthetic local-only credentials. PostgreSQL 18.1 runs at `127.0.0.1:55432`; API listens at `127.0.0.1:3000` (or `API_PORT`). Nothing is exposed on an external interface. Local Docker uses no paid account or external database. API and migration scripts use Node's built-in `--env-file=.env.local`; inherited shell variables take precedence. For an already-provisioned environment without a file, use package scripts `start:env` and `migrate:env` instead.

`pnpm build:api` builds contracts then API. `pnpm start:api` runs that compiled output. `pnpm dev:api` builds once, then Turbo runs the API's Node watcher and TypeScript watcher together; source edits compile into `dist/` and restart the API. Restart development after changing env values. Neither backend command starts Metro. `Ctrl+C` stops the server and watchers; Nest's SIGINT/SIGTERM hooks close HTTP and drain the DB pool. Then stop local PostgreSQL:

```bash
pnpm db:down
```

This removes the Compose project's container/network and preserves its named `postgres_data` volume. Shut down Docker Desktop too if you started it solely for this session. Do not stop unrelated containers. Local defaults are for development, not external rollout.

| Required server variable | Accepted value / role |
| --- | --- |
| `API_HOST` (optional) | `127.0.0.1` default, `0.0.0.0`, `::1` or `::`; image explicitly binds all IPv4 interfaces internally, runtime publishes only loopback |
| `API_APP_ENV` | `development`, `test`, `production` |
| `API_PORT` | Integer string, 1–65535 |
| `DATABASE_URL` | PostgreSQL URL with host/database; server-only, never a public Expo variable or log field |
| `API_ALLOWED_ORIGINS` | Comma-separated exact HTTP(S) origins, no whitespace/path/wildcard; empty string denies browser cross-origin access. Native clients without Origin still work |
| `API_LOG_LEVEL` | `error`, `warn`, `info`, `debug`; cumulative Nest log threshold |
| `API_AUTH_SECRET` | Server-only HMAC key, 32–256 characters, stable across restarts; synthetic local example must never be reused externally |
| `API_SMS_PROVIDER` | `development` (synthetic-only, forbidden in production) or `disabled` (OTP creation fails 503) |

`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT` are Compose-only values in the same example. Keep them aligned with `DATABASE_URL`. Changing these values does not rewrite credentials in an existing initialized data volume. Startup validates all seven server variables before creating Nest/pools; configuration errors never print values.

Probes use `GET /v1/health/live` and `GET /v1/health/ready`. Both return `{ data: { status: "ok" }, meta: { serverTime } }` on success. Liveness never queries DB; readiness checks the packaged migration manifest against the committed journal each time and returns raw `ApiErrorDto` / `SERVICE_UNAVAILABLE` with 503 on an outage. The lazy pool allows startup without DB. Since BE-006 readiness checks DB connectivity and exact migration-journal compatibility, not full schema drift or downstream providers. Connection timeout is 1 s; HTTP statement/client query timeouts are 2/3 s, pool maximum five connections.

Each request gets a new server UUID in `X-Request-Id`; incoming IDs are ignored to avoid propagating private caller text. Parser errors have IDs too. Domain/Zod errors use raw contract bodies, never an error wrapper; malformed JSON/schema errors are 422, unknown exceptions are safe 503. Unsupported routes remain transport 404, oversized JSON is transport 413 (16 KiB limit). Zod messages, dynamic paths/keys, body/header/query content, driver errors and connection URLs are not logged/echoed. The reusable Zod pipe requires an explicit schema per boundary; it does not invent business routes, coercion, auth or idempotency. Future dotted-query decoding remains assigned to consuming endpoints. Successful JSON uses the common server-time envelope, while 204 stays bodyless.

### SQL migrations

`pg` provides the pool and parameterized queries; no ORM, extra persistence layer or migration dependency. `apps/api/migrations/NNNN_snake_case.sql` contains immutable, ordered transactional SQL. The runner obtains transaction advisory lock `724001`, creates/checks `schema_migrations` (`name`, SHA-256 `checksum`, `applied_at`) and commits pending files plus journal atomically. Migration 0001 reserves schema `ride_match`; 0002 adds auth/places; 0003 adds rides/groups, private origins/meeting points, membership history, receipts, match sets and reference-only outbox; 0004 adds chat counters/intents/messages, blocks/reports and deferred block/membership checks; 0005 adds outbox ordering/metadata, match references/public versions, devices/session cleanup and reference-only push queue. Existing migrations remain immutable. Repetition applies zero files; concurrent runners serialize; edited/deleted/reordered applied history fails and errors roll back. Add new numbered files instead of editing applied files. No automatic migration on API startup, down/reset command or production migration rollout is implemented. Migrations allow 10 s statements / 11 s client query timeout and 5 s lock timeout; large future data migrations need their own reviewed strategy. Ship the `migrations/` directory alongside `dist/`.

## Local auth and places (BE-002)

The start/stop commands above are unchanged. On an existing BE-001 checkout, merge `API_AUTH_SECRET` and `API_SMS_PROVIDER` from `apps/api/.env.example` into ignored `.env.local`, then run `pnpm db:up`, `pnpm db:migrate` and `pnpm start:api`. Do not overwrite other local env values. This session prepared only synthetic local defaults. Existing DB upgrades apply one new migration; a fresh DB applies both, repeats apply zero.

Five auth endpoints (`/auth/otp/challenges`, `/auth/otp/verify`, `/auth/refresh`, `/auth/logout`, `/me`) and `/places/search` now use PostgreSQL. The development OTP provider accepts only Ofcom fiction numbers `+447700900000`–`+447700900999`; use synthetic code **123456**. **No SMS is sent.** Other numbers fail safely; production cannot enable this provider. `disabled` fails OTP creation explicitly; no real provider or account was provisioned. Never put the server HMAC key in Expo variables, logs or committed env files.

The key protects domain-separated phone, OTP, token and rate-limit verifiers. Only those digests are persisted; plaintext phone/code/tokens are not stored. Keep the key stable across restarts: changing it invalidates existing digests and is not a transparent rotation mechanism. Public users store a generated UUID, “Development rider” and null avatar. Auth identities, OTP challenges, sessions and credentials are separate tables. Old credentials/challenges/rate rows are not yet physically purged; retention/rotation before external use remains future operational work.

Policies: OTP 5 min / resend 30 s / five failed attempts; access 15 min; refresh 30 days, rotating both credentials. Known unexpired rotated-refresh replay revokes its family, including the winner of a simultaneous refresh. A lost refresh response therefore requires signing in again, not blind retry. A known rotated refresh can still revoke its family on logout (stricter than mock behavior); unknown/repeated logout is 204. Rate limits persist across process restarts: 60 requests/min per handler/TCP peer and five challenge requests/hour per phone. Proxy headers are ignored; trusted-proxy and distributed ingress protection are not implemented. Malformed JSON is body-limited but parsed before the DB rate guard. Responses are `no-store`, 429 also carries `Retry-After`.

Place search uses the documented dotted query keys, rejects unknown/duplicate/non-numeric keys and validates the reconstructed DTO. Anonymous access works; a supplied invalid or expired bearer fails. The catalogue has three clearly synthetic stable-ID landmarks and one coverage rectangle (42.80–42.95 N, 74.50–74.70 E). Search-center coverage is required; radius filters use straight-line distance. Query matches label/detail, prioritizing label prefixes then distance and ID. No match returns a real empty array; outside coverage returns `UNSUPPORTED_AREA`. This is not a real places provider or route algorithm.

No mobile env override, map key or native project was overwritten. Existing sign-in UI gets no mock `DemoSignIn`; the synthetic local number/code above are developer setup instructions, not real SMS credentials.

The first adapter was extended through BE-004 to auth/places/rides/groups/chat/safety. BE-005 implements devices and Socket.IO subscriptions too; there is no mock fallback. ## Local rides, discovery and groups (BE-003)

Start/stop/env commands are unchanged: `pnpm db:up`, `pnpm db:migrate`, `pnpm start:api` (or `pnpm dev:api`); `Ctrl+C` then `pnpm db:down`. No new variables/dependencies. Existing BE-002 DB upgrades with one migration; fresh DB applies three, repeat applies zero. Default mobile env remains mock; optional `.env.api.example` now covers auth/places/rides/groups. Native network/TLS and real SMS remain unconfigured.

All six ride methods and five group methods in BACKEND_HANDOFF now use the database. The initial public-origin policy is a stable 0.02° grid with 2 km uncertainty radius; exact origins are separate, owner-only. Matching is a same-public-venue, ≤5 min, ≤3 km coarse-area recommendation, with unknown additional/walking minutes. It is not route compatibility. Group destination/departure comes from the confirmed target; advisory matching does not replace join-time lifecycle/capacity checks. Meeting point is the nearest public landmark within 3 km, available immediately, member-only; source changes reopen ready groups. See [BE-003 policies](BACKEND_HANDOFF.md#be-003-local-policies-and-implementation) for deliberate differences from mocks.

`RideDomain.run` is the sole transaction boundary for reads/writes/expiry and future block-and-leave: advisory transaction lock 724003, lifecycle catch-up, then an action savepoint. Domain refusals roll back action writes but preserve deadline catch-up; internal DB failure rolls the whole transaction back. Partial unique indexes/seat bounds and deferred group/member constraints enforce core invariants. The coarse global lock and small catalogue/candidate scans are intentional local limits; this is not a load-tested production locking scheme. Do not call the boundary recursively or introduce writes outside it. A 30 s unref'ed worker is stopped/awaited before pool shutdown; lazy first tick preserves startup/liveness with DB down.

Requests expire after 15 min; grouped requests follow the group's 30 min deadline. Group expiry after a delayed restart uses the original deadline for closure/history (one hour), never restart time. `/me` now returns the actual latest request and live group references. Leave cancels the leaver, transfers coordinator by persisted join order and closes/cancels the remaining request below two members. No automatic re-search. Fourth member never auto-readies a group.

Mutation clients must send Idempotency-Key equal to operationId, including DELETE `/groups/{id}/members/me` with its JSON body. Receipts are actor/key with keyed canonical operation/path/input fingerprint. Group/private replay additionally requires the original still-readable membership epoch and unexpired closure access; leave/rejoin cannot revive it. Leave retry exposes owner-only result. Private payloads clear on leave/history expiry, all replay snapshots after 24 h; key/fingerprint tombstones stay and prevent re-execution. Retired matching keys fail VALIDATION_FAILED and require a current-state read; conflicting keys fail IDEMPOTENCY_CONFLICT. Outbox stores only committed resource-reference intents; BE-005 projects authorized wire events from these references.

Adapter validates requests/responses, dotted discovery keys and path IDs, sends mutation keys, supports PATCH/DELETE, translates device capturedAt using observed source offset and remembers the canonical wire input across lost-response retries. Intent state is in memory only and cleared on sign-out/disposal. The response envelope uses the same clock as domain timestamps, and `useClock`/cancel timeout use source presentation time. Device time/fix freshness on the native side is not mutated. Other-client state changes still need explicit/refocus HTTP reads until realtime exists; no polling or socket-success stub was added.

Verification: `pnpm build:api`; `pnpm --filter @ride-match/api typecheck`; `pnpm --filter @ride-match/api lint`; `pnpm test:api` (14 unit/HTTP checks); `pnpm test:api:integration` (27 PostgreSQL integration checks). The latter creates isolated local DBs, starts two independent Nest instances for real mobile-adapter journeys and cleans them up. It covers last-seat/canonical-group races, retries, restart/clock skew, public/private projections, membership/retention, meeting-point changes and SQL constraints. An additional addressed fault-injection run denied the second outbox intent after partial SQL writes, proved full rollback, then retried the same operation successfully. Focused mobile HTTP/data-source/sync and source-clock/request-card checks total five suites / 65 tests, with touched-file lint/typecheck. No full mobile/contract suite, Metro or native QA. Exact commands and intermediate fixes are in WORK_LOG.

## Local chat and safety (BE-004)

The same setup/start/stop commands and seven server variables apply; no new service, account or dependency. After `pnpm db:up`, use `pnpm db:migrate` to apply migration 0004 (or all four on an empty DB); repetition applies zero. Run API with `pnpm start:api` or `pnpm dev:api`, stop with Ctrl+C, then `pnpm db:down`. If Docker Desktop was started only for the session and no unrelated container is running, stop it too. If another project owns port 3000, keep it running and use `API_PORT=3001 pnpm start:api` (or dev:api); set the mobile API base URL to `http://127.0.0.1:3001/v1` for that run. Do not stop unrelated listeners or replace other local env settings.

Chat history/send and report/block/unblock/list use PostgreSQL and the mobile HTTP adapter. Chat send requires Idempotency-Key equal to clientMessageId; report/block match operationId. Unblock is bodyless DELETE/204. GET message pages use beforeCursor or afterSequence plus limit; blocks use cursor plus limit. Cursors are signed/group-or-owner scoped and must not be parsed by clients. No automatic mutation retry, synthetic reply, moderation workflow or per-operation mock fallback is supplied. Socket.IO is implemented by BE-005 below. BE-005 now delivers authorized events and recovers missed messages through authoritative HTTP rereads.

Ordered chat counter increments, text storage, intent and outbox reference commit together under the existing domain transaction. Block-and-leave shares the ordinary leave implementation and transaction; deferred DB checks prohibit blocked live pairs. Authenticated public candidates/direct reads check every participant. Anonymous browsing still exposes public projections; blocking is not anonymity from anonymous views. Full replay/error/privacy policies: [BE-004 handoff](BACKEND_HANDOFF.md#be-004-local-chatsafety-implementation).

**Local content retention:** message text/sender snapshots and queued message references are deleted at historyExpiresAt; intent metadata/digests/counters remain. Report contents/references and queued report references expire after 7 days. Generic snapshots retire at 24 h; message text never enters that journal. Retained closed history may be read/replayed only while entitled; leave/rejoin cannot replay a former membership's send intent. Sweep runs before every domain operation and every 30 s; downtime defers physical cleanup until restart/next operation, never extends access. These are live-table deletions, not WAL/backup erasure or production auth/location/metadata retention approval.

Verification commands remain `pnpm test:api` / `pnpm test:api:integration`; integration suites create/drop only their own random localhost databases. Address BE-004 alone with `node --env-file=.env.local --test tests/chat-safety.integration.mjs` from apps/api. It starts two ephemeral loopback APIs and loads only the real mobile transport/session modules, without Expo/Metro. Expected fault-injection diagnostics contain fixed event/request UUID only. Source uses transactional [UPDATE RETURNING](https://www.postgresql.org/docs/18/sql-update.html) and the existing [advisory transaction lock](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS), with no database sequence that could leave rollback gaps. ## Local realtime, devices and push boundary (BE-005)

HTTP remains usable on socket outages; no mutation queue/retry or mock fallback.

| Additional server config | Behavior |
| --- | --- |
| API_PUSH_PROVIDER | Optional `disabled` default or opt-in `expo`; external sending is disabled by the user's decision |
| EXPO_PUSH_ACCESS_TOKEN | Server-only printable token, required only for `expo`; never an Expo public variable, log, URL or committed value |

Optional build variable **EAS_PROJECT_ID** is a nonsecret UUID belonging to an existing EAS project, not a made-up production account. It enables extra.eas.projectId and the existing notifications plugin. No ID means no remote token/listeners; API mode never invents a demo token. A configured build requests real Expo tokens only after notification permission is granted, refreshes registration on native rotation/foreground and cleans listeners on disposal. APNs/FCM credentials, device rebuild and actual OS delivery still require setup and bounded device verification; none were provisioned/run here.

Server push uses fixed [Expo send/receipt APIs](https://docs.expo.dev/push-notifications/sending-notifications/) with generic copy and ID-only data, and an explicit disabled provider by default. A durable claim happens before POST; unknown outcomes/stuck sending are not automatically resent, so duplicates are avoided at the cost of possible loss. Tickets indicate Expo acceptance, not OS delivery. Receipts poll every 60 s; invalid tokens are removed only for their matching registration revision. Queue payloads are references only and are removed 24 h after expiry. Domain/session/device authorization is held through a bounded provider call; this serializes local throughput and requires redesign/load review before production. Readiness remains DB-connectivity-only, not provider/device readiness.

The [wire protocol and lock/recovery policies](BACKEND_HANDOFF.md#be-005-local-realtimedevicespush) fix the same Socket.IO 4.8.4 version on both ends. [Socket.IO delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/) do not replace the existing subscribe-before-snapshot/version/dedup/catch-up logic. Run `pnpm test:api:integration` or address only BE-005 from apps/api with `node --env-file=.env.local --test tests/realtime.integration.mjs`. Test push uses an injected provider with no external send and real local PostgreSQL/two loopback servers. Test resets serialize with the continuous worker rather than racing TRUNCATE. Stop API/watchers, `pnpm db:down`, and Docker Desktop when started solely for the task; preserve unrelated services and the development volume.

**Configuration files (DATA-001-A):** `apps/mobile/.env` (committed) sets the three public variables to the development values above. Override them in `apps/mobile/.env.local` (ignored) or the shell, then restart Metro: Expo reads `.env` when Metro starts and inlines `EXPO_PUBLIC_` values into the bundle. `src/config/appConfig.ts` validates them, with no defaults. A missing or invalid value, or `api`, replaces every route with a "This build can’t start" screen that names the variable; it never falls back to another data source. Jest loads no `.env`: `tests/setup/publicEnvironment.ts` sets the same development values. No credentials exist.

Public Expo variables are not secrets. API mode must fail clearly until implemented, never silently switch to synthetic riders. The scenario picker is limited to development/preview mock builds.

**Google Maps key for Android (MAP-001-A):** iOS draws Apple Maps and needs no key. Android draws Google Maps, which stops the app when a map appears without a key, so `app.config.ts` reads `GOOGLE_MAPS_ANDROID_API_KEY` and records only whether it was set (`extra.googleMapsAndroidConfigured`, read by `src/config/isMapProviderConfigured.ts`). Without it, Android shows "The map can't be shown in this build" with the sheet still working. To configure it:

1. In Google Cloud, create an API key, restrict it to Android apps with package `com.ridematch.dev` and the SHA-1 of the signing certificate (for development builds, `./gradlew signingReport` in `apps/mobile/android` prints the debug one), and restrict its APIs to Maps SDK for Android. Never paste the key into chat, docs, logs or tracked files.
2. Put `GOOGLE_MAPS_ANDROID_API_KEY=…` in `apps/mobile/.env.local` (ignored by Git). Expo CLI loads it when it evaluates the app configuration.
3. Regenerate the native project, since the key lives in the Android manifest (`apps/mobile/android/` is generated and untracked; remove it or run `pnpm exec expo prebuild --platform android --clean` in `apps/mobile`), then `pnpm mobile:android`. Restarting Metro alone changes the flag but not the manifest, and the app then stops when home opens.

The key goes through Expo's `android.config.googleMaps.apiKey`, which Expo keeps out of the public configuration served to the app; react-native-maps' own plugin options would have put it there.

Store future refresh credentials through SecureStore; keep access token in memory. Keep demo and production credential namespaces separate. Scenario reset clears demo state and this app's demo credentials only. No tokens or sensitive payloads in logs.

## Priority end-to-end flows

1. Anonymous browse -> destination -> auth -> create -> match -> group -> chat -> meeting point.
2. Empty map and denied/unavailable location.
3. Last-seat conflict and simultaneous join.

## Analytics boundary

Use typed `analytics.track(...)` events with bounded properties. Initially use an in-memory/no-op sink, inspectable in development. No vendor integration or external transmission is required.

| Event | Exact trigger | Stage and properties (ANALYTICS-001-A) |
| --- | --- | --- |
| `app_opened` | Start of a defined foreground session | view; — |
| `map_opened` | Main map first becomes visible in that session | view; — |
| `nearby_activity_exposed` | Fresh successful discovery renders; record zero/nonzero and count bucket | view; `countBucket` (`0`, `1`, `2-5`, `6-20`, `21+`), `truncated` |
| `nearby_marker_seen` | Peer marker visible for a minimum dwell; deduplicate per session | view; `kind` (`ride`, `group`) |
| `nearby_marker_tapped` | Peer marker tap | intent; `kind` |
| `destination_selected` | Search suggestion confirmed | intent; — |
| `ride_request_create_clicked` | User confirms creation intent | intent; `departureOffsetMinutes` (0, 5, 10), `pickup` (`device`, `manual`) |
| `ride_request_created` | Canonical create succeeds | success; `departureOffsetMinutes`, `pickup` |
| `ride_request_expired` | Authoritative expiry observed, once per request | observed; — |
| `match_found` | New valid match observed, once per match/version | observed; `level` (`possible`, `good`, `excellent`), `kind` |
| `group_join_clicked` | Join intent confirmed | intent; `kind` |
| `group_joined` | Canonical membership succeeds | success; `kind`, `memberCount` (2–4) |
| `group_leave_clicked` | Leave intent confirmed | intent; — |
| `group_left` | Canonical removal succeeds | success; — |
| `message_send_clicked` | User submits text | intent; — |
| `message_sent` | Canonical message accepted | success; — |
| `meeting_point_viewed` | Meeting-point detail opened | view; — |
| `taxi_open_clicked` | External handoff requested | intent; — |
| `taxi_opened` | OS accepts handoff; not proof of native opening or booking | success; — |
| `ride_completed` | Explicit completion mutation succeeds | success; `memberCount` |
| `user_reported` / `user_blocked` | Corresponding operation succeeds | success; `reason` (the four report reasons) / — |

Properties may include environment, application version, mock scenario ID, session ID, and pseudonymous installation/user identity. Do not accept unrestricted metadata. Exclude phone numbers, coordinates, destination search text, messages, report content, and credentials. Never emit success solely because a button was pressed.

Session/dwell thresholds should be defined and tested in ANALYTICS-001. Synthetic scenario traffic must remain distinguishable and excluded from future real-user metrics.

**Implemented (ANALYTICS-001-A):** `apps/mobile/src/analytics/`. Since MAP-002-A the composition root creates the client and the root layout starts it (`map_opened`, `nearby_activity_exposed` are the first tracked events).

- `events.ts`: the catalog above, one fixed set of required properties per event, built from contract enums and small whole-number ranges only. The types reject other properties at compile time, and `validateEvent` rejects an unknown event, an extra property (such as a coordinate, phone number, search text, message or report details) or a missing or out-of-range value at run time with an `AnalyticsEventError` that names the property but never the value. Nothing invalid is recorded. Stages: `view`, `intent` (asked for), `success` (only from the source's canonical result) and `observed` (a source change the user did not cause); `INTENT_SUCCESS_PAIRS` lists the five intent/success pairs. `countBucket` turns a visible count into a bucket, so no exact count is recorded.
- `createAnalytics.ts`: `track`, `trackOncePerSession` (such as `map_opened`), `trackOnce(key, …)` (such as one expiry per request; the key stays on the device), `markerVisible`/`markerHidden` and `setUser`. Every event carries its stage, session ID, sequence, time and context: environment, app version, mock scenario, `synthetic` (true on the mock data source), installation ID (`null` until one is stored) and pseudonymous user ID.
  - **Session:** `start()` begins the first one with `app_opened`, at once or on the first foreground. A return after `SESSION_TIMEOUT_MS` (30 minutes) or more in the background begins a new one; a shorter absence or iOS `inactive` continues it.
  - **Dwell:** a peer marker (never a cluster or the user's own) counts as seen after `MARKER_DWELL_MS` (1 second) of foreground visibility, once per target per session, recording only its kind. Going to the background pauses the dwell; hiding the marker cancels it.
- `sinks.ts`: `createMemorySink` (keeps the latest 500 for inspection), `noopSink`, and `selectAnalyticsSink` (memory in development and preview, nothing in production). Nothing leaves the device. `isRealUserEvent` keeps only production events from a real data source, so every mock event is excluded.
- `AnalyticsProvider` and `useAnalytics()` hand the client to features.

## Retention hypothesis

Hypothesis: users exposed to at least one nearby active ride engage and return more often than users seeing an empty map.

- Cohort by the first eligible successful map exposure, not a failed or loading screen.
- Distinguish zero visible peer activity from at least one visible peer activity item.
- Exclude own markers, stale data, failed loads, and mock sessions.
- Track clustered visible activity for the exposure metric without inventing individual marker impressions.
- D1/D7 are return sessions on UTC calendar day 1/day 7 after cohort entry.
- Preserve anonymous-to-authenticated association with pseudonymous IDs, never phone numbers.
- Instrumentation is verifiable now; actual retention requires a future analytics destination and real users.

Open anonymously -> nearby activity -> destination -> authentication gate
